## Ordered steps
1. **Checker and tests** — tests first, seen red, then `tools/spec-design-reference.ts`:
   - `Status:` from the `- Status:` line. Only `Approved` and `In progress` are judged (G4). `Draft` and others pass.
   - **Full spec** (has `## User experience`): take that section's text with HTML comments removed. If it begins
     with `none — no user interface`, the spec has no UI and passes (G1). Otherwise a `- Design reference:` line in
     that section must match either
     `^(https://claude\.ai/(code/)?artifact/[A-Za-z0-9-]+) · version: (\S.*?) · approved (\d{4}-\d{2}-\d{2})$`
     or the waiver `^none — waived by (\S.*?), (\d{4}-\d{2}-\d{2}), (\S.*)$` (G2). Anything else is a violation
     that names the file and shows the expected format. That includes a missing line, another URL, a chat link,
     a missing version, the template wording "none — the flow above is the design" (G5), and a waiver missing a part.
   - **Mini-spec** (no `## User experience`, has a `- Design:` header line): when the value is filled in (not empty
     or comment-only), it must match the same link or waiver format (G6, see Risk 2).
   `[plan 0002/1]`
2. **Docs** — the `docs/testing.md` section covers: when a design is needed; that the Analyst creates or reuses a
   Claude Design artifact (Artifact tool, Design type) showing every listed state; that it publishes it with the label
   `spec NNNN approved` right before the spec approval gate and records link, label and date; the waiver form; that the
   artifact isn't republished until the spec ships, except through an R-08 spec change (new label); that VERIFY compares
   screenshots with it (content, structure and states, not pixels); and that the ANEW template wording is not accepted.
   Plus the pointers in `docs/conventions.md` and `CLAUDE.md`. `[plan 0002/2]`
3. **Evidence** — `dash ./scripts/check` full and `--fast`, a test-count check, Build evidence, push, draft PR. `[plan 0002/3]`

## Risks & open questions
1. **Version identifier (spec G3).** The Artifact platform lets a publish carry a `label` (≤ 60 chars), and the
   artifact keeps a version history, but I haven't confirmed that a URL can open one exact past version.
   *Recommendation:* the identifier is the label `spec NNNN approved`, and the docs forbid republishing the design
   until ship except through an R-08 spec change. The current version therefore *is* the pinned one when VERIFY
   reads it. If a platform version ID turns up later, adopting it is a CHANGE-lane mini-spec.
2. **Mini-specs and "touches a UI" (spec G6).** The mini template has no User experience section, only a
   `- Design:` field marked "UI change only". Check can't tell on its own whether a change touches a UI.
   *Recommendation:* check validates the format of a filled-in `- Design:` value, and whether a UI-touching mini-spec
   left it empty is a review question, as `docs/testing.md` will say. This is a limit of the template, not a gap in
   the spec, and it is written down rather than smuggled in.
3. **check only reads the files.** It never opens the link (out of scope: check runs offline). An artifact the
   reviewer can't open is a review finding. *Recommendation:* accept.
4. **Environment (R-13):** doctor today shows profile fast and full runnable on this machine, 0 fail / 0 warn.
   check.conf is unchanged. Locally check and doctor run via `dash` (B-1).
